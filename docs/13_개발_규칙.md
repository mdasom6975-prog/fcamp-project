# 13. 개발 규칙 (브랜치·커밋·릴리스)

> 초안 — 2026-10-22. 혼자 개발하는 프로젝트라 가볍게 유지한다. 규칙이 일을 막으면 이 문서를 고친다.
> 계획은 `docs/12_로드맵.md`, 변경 이력은 `CHANGELOG.md`.

## 1. 브랜치

| 브랜치 | 역할 | 규칙 |
|---|---|---|
| `main` | 릴리스. 태그(`vX.Y.Z`)가 붙은 상태만 | 직접 커밋하지 않는다. develop 을 병합해서만 갱신 |
| `develop` | 통합. 다음 릴리스 후보 | 기능 브랜치를 병합해서 갱신. 항상 테스트가 통과해야 한다 |
| `feat/<이름>` | 기능 추가 | develop 에서 분기 → develop 으로 병합 |
| `fix/<이름>` | 버그 수정 | 위와 같음 |
| `docs/<이름>` · `chore/<이름>` | 문서·설정·정리 | 위와 같음 |
| `hotfix/<이름>` | 배포된 main 의 긴급 수정 | main 에서 분기 → main 과 develop 양쪽에 병합 |

- 이름은 짧은 한글·영문 모두 가능하다: `feat/캠페인-삭제`, `fix/본문-누락`, `docs/로드맵`.
  Claude Code 워크트리가 만드는 `claude/<이름>-<해시>` 는 임시 이름이다. 작업 주제가 정해지면 의미 있는 이름으로 바꾼다
  (`git branch -m`). 병합이 끝난 브랜치와 워크트리는 바로 지운다.
- 한 브랜치는 이슈(또는 로드맵 항목) 하나만 다룬다. 두 가지를 같이 하게 되면 브랜치를 나눈다.
- 병합: 이력이 한 줄로 이어질 수 있으면 fast-forward(필요하면 분기 브랜치를 develop 위로 rebase),
  아니면 병합 커밋. **push 하지 않은 커밋만** rebase 한다. push 한 이력은 고쳐 쓰지 않는다(force push 금지).

## 2. 커밋

- 제목은 한국어 한 줄, **무엇을 + 왜**(결과 중심). 예: `시안(A/B/C)을 바꾸면 이미 만든 합성본도 새 문구로 자동 재합성`.
- 본문(필요할 때): 변경 요점을 `-` 목록으로, 원인·방침처럼 코드에 안 남는 이유를 적는다.
- 한 커밋 = 하나의 논리적 변경. 성격이 다른 수정(예: 문구 자리 수정과 시안 재합성)은 커밋을 나눈다.
- 커밋하기 전에 통과해야 하는 것:
  ```bash
  .venv/bin/python -m pytest tests -q        # 저장소 루트의 backend 가상환경으로
  cd frontend && npx tsc -b                  # 타입 검사
  ```
  린트(`npx oxlint src`)의 기존 경고는 무시하되, **새 경고는 만들지 않는다**.
- 커밋하지 않는 것: `backend/data/`(옛 로컬 DB·로그), `backend/storage/`(파일 캐시), `.env`, `node_modules`, `frontend/dist`.
  키·비밀번호는 절대 커밋하지 않는다(`.env.example` 만 커밋).
- 디자인·프롬프트처럼 결과를 눈으로 봐야 하는 변경은 화면(또는 생성 결과)을 확인한 뒤 커밋한다.

## 3. 이슈와 작업 흐름

1. `docs/12_로드맵.md` 표에서 항목 하나를 고른다(높음부터).
2. 이슈를 만든다(제목 = 항목명, 본문 = 수용 기준, 라벨·마일스톤은 아래 표).
3. `develop` 에서 `feat/…` 또는 `fix/…` 브랜치를 만든다.
4. 구현 → 테스트 추가 → 화면 확인 → 커밋. 이슈 번호는 커밋 본문 또는 병합 메시지에 `#번호` 로 남긴다.
5. develop 에 병합하고 브랜치·워크트리를 지운다. 로드맵 표의 해당 항목에 완료 표시를 한다.
6. 사용자에게 보이는 변경은 `CHANGELOG.md` 의 `[Unreleased]` 에 한 줄 추가한다.

이슈 라벨(처음 쓸 때 만든다):

| 라벨 | 뜻 |
|---|---|
| `우선:높음` / `우선:중간` / `우선:낮음` | 로드맵 우선순위 |
| `유형:기능` / `유형:버그` / `유형:문서` / `유형:정리` | 작업 종류 |
| `영역:브랜드` / `영역:카피` / `영역:이미지` / `영역:편집` / `영역:검수` / `영역:배포` | 화면·기능 영역 |

마일스톤은 `v0.10`, `v0.11`, `v1.0` 세 개. 이슈 템플릿(초안):

```markdown
## 무엇이 문제인가 / 무엇을 만드는가
## 수용 기준
- [ ] …
## 참고
(로드맵 항목, 문서 08 절 번호, 스크린샷)
```

## 4. 버전과 릴리스

- 버전: `vMAJOR.MINOR.PATCH`. v1.0 전에는 **마일스톤 하나 = 마이너 버전 하나**(v0.10, v0.11). 같은 마일스톤 중간에 급히
  고친 것은 패치(v0.10.1).
- 릴리스 절차 (develop 이 릴리스 후보일 때):
  1. `CHANGELOG.md` 의 `[Unreleased]` 를 새 버전 절로 옮기고 날짜를 적는다 → 커밋(`docs: v0.10.0 변경 이력`).
  2. 테스트·타입 검사 통과, 로컬에서 핵심 흐름 한 번 완주.
  3. main 에 develop 을 병합한다.
     ```bash
     git checkout main && git merge --no-ff develop -m "v0.10.0 릴리스"
     git tag -a v0.10.0 -m "v0.10.0: 한 줄 요약"
     git checkout develop && git merge main      # 병합 커밋이 있으면 develop 에도 반영
     ```
  4. 사용자가 직접 push(브랜치와 태그): `git push origin main develop --follow-tags`
  5. 배포가 필요하면 `docs/11_Vercel_Supabase_배포.md` 절차를 따른다.
- 현재 태그: `v0.9.0` (2026-10-22, develop 기준 로컬 태그. 원격에는 사용자가 push 해야 올라간다).

## 5. 로컬 데이터와 환경

- 로컬 개발은 Supabase **dev 프로젝트**(Postgres + Storage)를 쓴다. `backend/.env` 의 `DATABASE_URL`·`SUPABASE_*` 가 dev 값이어야 하고,
  prod 값을 넣으면 로컬에서 운영 데이터를 고치게 되므로 두 프로젝트의 값을 섞어 두지 않는다. `backend/storage/` 는 내려받은 파일의 캐시일 뿐이다(지워도 된다).
  dev 를 비우고 다시 채우려면 Supabase 대시보드에서 표를 비우거나 `tools/sync_env.py --replace`(prod 와 같게), 처음부터는 `tools/seed_env.py`.
- 테스트는 `tests/conftest.py` 가 임시 Postgres 를 띄워 돌리므로 dev·prod 어느 쪽도 건드리지 않는다. 바이너리는 conda-forge(`pgtest` 환경).
- 포트: 백엔드 8000, 프론트엔드 5173. 개발 서버를 켜 둔 채 브랜치를 바꾸면 이전 코드가 계속 실행되니, 브랜치를
  바꾸거나 병합한 뒤에는 서버를 재시작한다.
- 모델 호출은 비용이 든다(`docs/12` v0.10 과금 표시 참고). 테스트와 격리 확인에는 임시 DB·임시 저장소를 쓰고
  dev·prod 데이터는 건드리지 않는다.

## 6. AI 도구(Claude Code)와 일할 때의 합의
- 수정 전에 방안을 보여 주고 승인받은 뒤 고친다. 되돌릴 수 없는 일(삭제·강제 변경)은 범위를 확인받는다.
- 커밋은 요청할 때만 한다. 커밋 메시지 끝에 공동 작성자 표기를 붙인다.
- push 는 사용자가 직접 한다. 이슈 생성처럼 원격에 올라가는 일도 승인 후에만 한다.
- 파일 정리·삭제는 사용자가 직접 하거나 범위를 지정해서 맡긴다(용량 원인은 `.venv`·`node_modules`).

## 법적 규칙 점검 (prompts/legal/)

- 정기적으로 `backend/.venv/bin/python tools/check_legal_sources.py` 를 실행한다. 변경이 나오면 영향받는 규칙을 검토·수정하고 `--update` 로 기준을 갱신한다
